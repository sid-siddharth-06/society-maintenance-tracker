# System Design: Society Maintenance Tracker

The Society Maintenance Tracker is a Next.js-based web application for managing residential maintenance complaints. It uses server-side authentication, role-based authorization, PostgreSQL persistence, Cloudinary for complaint photos, and Resend for email notifications.

## 1. Overall Architecture

The application uses the Next.js App Router and is deployed on Vercel. Requests are handled through Next.js Route Handlers and Server Actions. Authentication is provided by Auth.js using secure HTTP-only JWT session cookies.

The application defines two roles: `ADMIN` and `RESIDENT`. Server-side authorization utilities enforce RBAC for protected operations. Residents can access only their own complaints, while administrators can manage all complaints and system configuration.

Prisma ORM provides database access to PostgreSQL hosted on Neon. The current production configuration uses Prisma with `@prisma/adapter-pg` and the native `pg` driver.

External services are isolated behind server-side integrations:
- Cloudinary handles complaint photo storage.
- Resend handles email notifications.
- Vercel hosts the Next.js application.

## 2. Complaint History Model

Each complaint follows a controlled lifecycle:

`OPEN → IN_PROGRESS → RESOLVED`

Every successful status transition creates a `ComplaintHistory` record containing the complaint reference, previous status, new status, actor, optional note, and timestamp.

Status updates and history creation are performed inside a Prisma `$transaction`, ensuring that the complaint status and its corresponding history record are committed atomically.

The actor identity is derived from the authenticated server-side session rather than client input. Similarly, timestamps are generated by the database/application rather than accepted from the client. History records have no update or delete API, making the history effectively append-only and immutable.

## 3. Overdue Detection

The SLA system uses the `SystemConfig` database table as the source of truth for `OVERDUE_THRESHOLD_DAYS`.

The server calculates whether an unresolved complaint has exceeded the configured threshold based on its `createdAt` timestamp and the current server time. `RESOLVED` complaints are always excluded from overdue calculations.

The same SLA logic is reused by complaint retrieval and the administrator dashboard. Overdue complaints are surfaced before normal complaints, allowing administrators to identify delayed maintenance requests quickly.

## 4. Photo Handling

Residents can optionally attach a photo when creating a complaint. The application accepts the supported image formats and enforces the configured file-size limit on the server.

The browser sends the file to the Next.js complaint API using `multipart/form-data`. The server validates the file before uploading it to Cloudinary using server-side credentials.

Cloudinary returns a secure URL after a successful upload. Only this server-generated URL is stored in the complaint's `imageUrl` field. Cloudinary credentials are never exposed to the browser, and clients cannot directly inject an arbitrary image URL.

## 5. Notification Flow

Resend provides email notifications for complaint status changes and important notices.

For a complaint status update, the database transaction first updates the complaint and creates its history. Only after the transaction succeeds does the server retrieve the resident's email from PostgreSQL and attempt delivery through Resend.

For an important notice, the notice is first persisted successfully. The server then retrieves eligible resident email addresses from the database and attempts the notification.

Email delivery is intentionally isolated from the primary database operation. If Resend fails, the error is handled server-side without rolling back the already successful complaint or notice operation. This prevents an external email-service failure from corrupting core application state.
